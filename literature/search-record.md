## Part B. Execution

What actually ran. Part A is the strategy a reader would run to
reproduce the search; this is the log of the searches issued on
2026-09-06. The two differ, and printing both is the point.

The queries were issued against PubMed through its E-utilities, against
Crossref, Europe PMC, DataCite, OpenReview and DBLP through their REST
endpoints, and against publisher and repository pages through web search
restricted to those domains and through direct fetch. They are not the
rendered platform strategies of Part A pasted into each platform's search
box: no institutional Scopus or Web of Science credential was available,
and PubMed was driven through its API rather than its web form.

The log is grouped by concept block rather than ordered in time, because
the four blocks were searched independently of one another.

The returned column is as the interface reported it. Where a query
returned nothing that is recorded too, because a zero is the evidence
behind several of the absence statements in the related-work section.

Each row gives the search id, the corpus searched and the interface it
was reached through, the query as issued, what the interface reported
back, and what was carried into screening. The corpus and the interface
are reported separately because they are separate claims: a query run
against PubMed through its API and the same query typed into its web
form return different sets, and a reader reproducing this needs to know
which.

**The taken-forward column does not exist for blocks b2, b3, b4.**
Those logs were written without it and it was never captured, so it
reads as not recorded rather than as nothing taken. What each of those
searches contributed is in the screening decisions, which carry every
included and every excluded record with a reason; this column, where it
exists, is a convenience and not the evidence.
